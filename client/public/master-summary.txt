# 1) Core “Thin Wrapper” Test (Most Important)

1. If this web app were embedded in a WKWebView as-is, would Apple likely classify it as a “thin wrapper”? Why or why not?
Yes—based on the current code, it looks like a standard SPA with web routing, web UI components, and network fetch calls for core gameplay data, with only minimal browser storage usage. There are no native integrations or device-specific features surfaced in the code, so Apple would likely see it as a wrapped website. The app routes purely via a web router and renders web pages (Landing, Game, Terms, Privacy).【F:client/src/App.tsx†L1-L35】 Core game state and data (properties, deals, ledger, week progression, purchases, hall of fame) are fetched over HTTP via /api endpoints using fetch, which is standard web behavior rather than native app integration.【F:client/src/lib/api.ts†L1-L235】 The only client-side persistence shown is sessionStorage for a game run ID and skipped diligence flags, which is a typical browser feature, not a native capability.【F:client/src/pages/Game.tsx†L51-L140】

2. Which parts of the current web app would feel indistinguishable from Safari inside an iOS container?
The entire UI is built as web pages and web modals with Tailwind-style classes and wouter routing. The landing page, player name modal, premium modal, and menu overlay are all standard web UI patterns (buttons, modals, overlays, client-side routing).【F:client/src/pages/Landing.tsx†L6-L89】【F:client/src/components/game/PlayerNameModal.tsx†L10-L84】【F:client/src/components/game/PremiumModal.tsx†L105-L245】【F:client/src/components/game/StatusBar.tsx†L98-L260】 This would render and behave the same inside Safari or a WKWebView.

3. What minimum native features would be required to make this app clearly not just a website?
At minimum, you’d want one or more of:
- Offline/local save + resume implemented with native storage (e.g., Core Data) rather than sessionStorage.
- Native onboarding (e.g., native screens, Apple sign-in, permissions).
- Native gestures/haptics tied to game actions (e.g., haptic on deal commit, system-level gesture nav).
- Background notifications (e.g., “rent payment posted” or “week advanced” reminders).
These would be distinct from the current web-only pattern of fetch calls + browser storage.【F:client/src/lib/api.ts†L1-L235】【F:client/src/pages/Game.tsx†L51-L206】

# 3) Offline / Resilience Expectations

7. What currently happens if the app is opened without an internet connection?
Given that core data is fetched from /api endpoints, the app would fail to load game content when offline. The Game page shows a loading spinner while data is fetched, and if errors are set, it displays a generic “Failed to load game” state with a “Try Again” button (which would still fail offline).【F:client/src/pages/Game.tsx†L636-L689】【F:client/src/lib/api.ts†L7-L186】

8. Could the app display an offline screen / cached state / resume last session without major changes?
Not as-is. There’s no service worker, caching layer, or local persistence for game state; the data flow depends on live API calls for game runs, deals, ledger entries, and property data. Implementing offline mode or cached resume would require adding local persistence and/or caching strategies to replace or supplement server calls.【F:client/src/lib/api.ts†L7-L186】【F:client/src/pages/Game.tsx†L148-L206】
